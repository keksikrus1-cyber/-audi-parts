# MVP Plan — AudiParts

## Цель MVP

Запустить веб-платформу для поиска и сравнения цен на запчасти Audi в России. Покупатель вводит запрос, VIN или артикул — и видит предложения от нескольких поставщиков с ценами, сроками доставки и возможностью добавить в корзину.

## Стек

| Слой | Технология |
|------|-----------|
| Backend | Bun + Hono + Prisma + PostgreSQL |
| Frontend | React 19 + Vite + TanStack Router/Query + shadcn/ui + Tailwind v4 |
| Contracts | Shared Zod-схемы (`@autoparts/contracts`) |
| Платежи | ЮKassa (сплит-платежи) — отложено |
| Mobile | Expo — отложено |
| Деплой | Не планируется сейчас |

## Что входит в первую версию

- Поиск запчастей: по названию, VIN, артикулу
- Каталог с фильтрами и сортировкой
- Карточки товаров с mock-данными поставщиков
- Сравнение цен от нескольких поставщиков
- Страница моделей Audi с поколениями
- Корзина
- Избранное
- Авторизация (покупатель)
- Кабинет поставщика (базовый)
- Админка (базовая)
- Заказы

## Что отложено

- Мобильное приложение (Expo/React Native)
- Landing-страница (Astro)
- Реальные интеграции с поставщиками (Exist.ru, Emex.ru, Autodoc, Avtoall)
- Реальные платежи через ЮKassa
- Production-деплой
- Поддержка других марок (BMW, Mercedes, Volkswagen)
- Сплит-платежи
- Maestro E2E

## Роли

| Роль | Описание |
|------|----------|
| `buyer` | Покупатель: поиск, корзина, заказы, избранное |
| `supplier` | Поставщик: управление товарами и ценами |
| `admin` | Администратор: управление пользователями, поставщиками, заказами |

## Основные сущности

| Сущность | Описание |
|----------|----------|
| `users` | Пользователи (buyer, supplier, admin) |
| `products` | Запчасти (артикул, название, категория, совместимость) |
| `suppliers` | Поставщики (название, рейтинг, условия) |
| `supplierProducts` | Предложения поставщика: цена, наличие, срок доставки |
| `cartItems` | Позиции корзины |
| `orders` | Заказы |
| `orderItems` | Позиции заказа |
| `favorites` | Избранные товары пользователя |
| `vinRequests` | История VIN-запросов |

## API-модули

| Модуль | Эндпоинты |
|--------|-----------|
| `auth` | register, login, logout, me |
| `products` | list, get, search (по запросу, артикулу) |
| `vin` | decode (mock → real) |
| `suppliers` | list, get, products |
| `cart` | get, add, update, remove, clear |
| `orders` | create, list, get |
| `admin` | users, suppliers, orders |

## Этапы реализации

### Этап 0 — Подготовка проекта ✅
- Переименование в AudiParts / autoparts-marketplace
- Сохранение HTML-дизайна как design reference
- Создание документации (DESIGN_REFERENCE, UI_COMPONENT_MAP, MVP_PLAN)
- Первый commit и push

### Этап 1 — Перенос дизайна из HTML-макета в web
- Перенос CSS-переменных и базовых стилей
- Создание компонентов по UI_COMPONENT_MAP.md
- Статичные страницы с mock-данными
- Без backend, без API

### Этап 2 — Mock-каталог
- Полностью рабочий UI на mock-данных
- Поиск, фильтры, сортировка
- Корзина (localStorage)
- Избранное (localStorage)

### Этап 3 — Backend schema
- Prisma schema: все сущности из раздела выше
- Docker Compose PostgreSQL
- Миграции

### Этап 4 — API
- Hono routes для всех модулей
- Zod-валидация через contracts
- Mock-данные в БД (seed)

### Этап 5 — Авторизация
- JWT auth (register/login/me)
- Роли: buyer, supplier, admin
- Защищённые роуты

### Этап 6 — Корзина
- Корзина через API (не localStorage)
- Группировка по поставщикам

### Этап 7 — Кабинет поставщика
- Управление товарами и ценами
- Просмотр заказов

### Этап 8 — Админка
- Управление пользователями
- Управление поставщиками
- Просмотр всех заказов

### Этап 9 — Заказы
- Создание заказа из корзины
- История заказов покупателя
- Статусы заказов

### Этап 10 — Подготовка ЮKassa
- Интеграция тестового режима ЮKassa
- Без реальных платежей

### Этап 11 — Тестирование
- Playwright E2E для критических сценариев
- Backend integration tests

## Правила работы с дизайном

1. **HTML-макет — источник правды.** Файл `docs/design/audi-parts-reference.html` определяет все визуальные решения.
2. **Нельзя менять стиль без разрешения.** Цвета, отступы, типографика, сетка — только из макета.
3. **Переносить интерфейс постепенно.** Один компонент за раз, сверяя с макетом.
4. **Сначала web на mock data, потом backend.** Не блокировать UI-работу ожиданием API.
5. **Обновлять UI_COMPONENT_MAP.md** при создании каждого компонента.
6. **Не придумывать новые UI-паттерны** — если чего-то нет в макете, сначала предложить план.
